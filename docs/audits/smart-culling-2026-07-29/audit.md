# 智能选图二次审计

日期：2026-07-29
审计对象：当前工作区源码与本机重新构建的 macOS 客户端
评估目标：判断现有代码逻辑和 UI 交互是否足以支撑已确认的专业摄影师智能选图需求

## 结论与置信度

结论：**当前实现不能支撑已确认需求，也还不能作为可交付的智能选图版本。**

QRaw 已经具备可复用的安全底座，但“智能判断、关键人物、故事/相似组、专业复核、窗口适配”仍需要在 `src/features/smart-culling` 与 `src-tauri/src/features/smart_culling` 内进行一次中等规模、功能域内的重构。无需污染上游编辑器主流程，也不需要推翻已经完成的数据安全能力。

- 对“当前版本不能支撑需求”的判断置信度：**97%**
- 对“主要问题类别没有遗漏”的判断置信度：**95%**
- 不能声称 100% 的原因：尚未完成 Windows 真机、1000 张真实 RAW/JPEG 标注集、不同 DPI/色彩空间和系统级辅助功能测试。

## 本次证据范围

本次不是只读代码推断，而是同时完成：

1. 重新构建当前客户端。
2. 在 Apple Silicon Mac 上实际运行完整的配置、关键人物、分析、复核流程。
3. 验证 961×601 最小桌面窗口与 1404×768 最大窗口。
4. 使用 17 张连续人像样本执行一次真实离线分析。
5. 复核前后端数据契约、状态事件、渲染输入、模型、评分、分组、保护和写入代码。
6. 运行现有 Rust 智能选图测试和项目构建检查。

## 已确认的 P0 问题

### 1. 关键人物识别流程会被状态事件中断

实际操作“选择关键人物 → 选择照片 → 识别照片人物”后，识别完成事件立即把界面切回配置页，无法继续点击识别到的人脸。

原因是命令调用虽然使用 `preserveScreen=true`，但 `useSmartCullingEvents.ts` 收到 `configuring` 快照后仍无条件调用 `screenForSnapshot()`，把前端屏幕改为 `setup`。这是两套屏幕状态规则相互覆盖，不是单纯的视觉问题。

### 2. 人脸框坐标在非同宽高比下必然错误

`PeopleScreen.tsx` 把标准化人脸框百分比直接定位到整个 `.sc-person-stage`；图片却使用 `object-fit: contain`。出现上下或左右留白时，框的百分比坐标仍以容器为基准，而不是以实际图片内容矩形为基准，因此位置和尺寸都会偏移。

当前没有 `ResizeObserver`、图片内容矩形、缩放矩阵或坐标换算层。

### 3. 关键人物没有专业查看能力

当前只有静态 `<img>`：

- 不能缩放；
- 不能平移；
- 不能 100% 查看眼睛和人脸；
- 没有双击适配、滚轮缩放、触控板手势；
- 没有键盘切图；
- 缩略图缺失时只显示文件名；
- 人脸选择结果没有稳定的当前选中视觉状态。

### 4. 关键人物显示图和检测图没有统一数据契约

后台在 `render_current_state()` 产生的完整当前渲染图上检测；前端显示的是图库通用缩略图。两者由不同代码路径产生，没有共享预览尺寸、裁剪矩形、方向、内容区域或变换矩阵。即使修正 `object-fit`，也仍需建立“检测坐标对应哪一张显示图”的显式契约。

### 5. 当前分析没有完成“选图”

真实运行结果：

- 17 张连续人像被拆成 17 个“单张故事”；
- 默认采用 17 张；
- 精选 9、待确认 8、淘汰建议 0；
- 每个单张故事都显示“建议保留 1”。

因此它完成的是批量评分和着色，不是从连续拍摄中减少摄影师工作量的选图。

根因包括：

- 相似分组只使用整图感知哈希和固定距离阈值；
- 不使用拍摄时间、序号、EXIF、连拍间隔、主体/人脸身份或语义特征；
- 1–5 张的组全部保留；
- “故事”只是相似组编号，不是事件或叙事覆盖；
- 本次视觉上明显相关的连续人像未被分为同组。

### 6. 九种模式大部分只是固定权重和文案

现有真实信号只有：

- 全局拉普拉斯清晰度；
- 中央区域清晰度；
- 灰度直方图曝光；
- 人脸数量；
- 眼睛开闭；
- 关键人物近似匹配。

没有场景分类、主体检测、构图、动作、遮挡、表情质量、重复内容、故事覆盖、动物眼睛、建筑透视、星点质量、产品背景等对应能力。`auto` 模式甚至把“无人脸的横图”判为风光，把“无人脸的竖图”判为产品。

### 7. 关键人物匹配不是身份识别

当前把人脸裁剪做感知哈希，再以固定距离判断是否同一人物。感知哈希适合近似画面，不是人脸身份特征；姿态、光线、表情和尺度变化都会显著影响结果，也可能把相似外观的人误判为同一人。

### 8. 置信度不是经过校准的可信度

置信度由评分离 0.5 的距离计算，并固定限制在 50%–96%。它没有使用验证集校准，也不表示模型预测正确率。UI 将其显示为“70%”会给用户造成统计可信度的误解。

## 已确认的 P1 UI/交互问题

### 响应式布局

`.sc-page` 自身设置 `min-width: 960px`，但它还嵌在约 264px 的图库侧栏之后。961px 应用窗口内，智能选图实际可用宽度远小于 960px，所以整页水平溢出。

- 配置页固定 `218px + minmax(600px) + 260px`；
- 关键人物页固定 `minmax(620px) + 310px`；
- 复核页在唯一断点后仍固定 `180px + minmax(480px) + 250px`；
- 唯一的 `@media (max-width: 1120px)` 没有处理关键人物页，也没有覆盖更小窗口；
- 分析进度浮层固定宽 790px。

最小窗口中配置摘要、人物优先级面板、复核检查器和确认入口都出现不可见或部分不可见。

### 专业复核工具缺失

现有复核页没有：

- 同组并排比较；
- A/B 或多图对比；
- 同步缩放和平移；
- 100% 放大镜；
- 对焦区域、人脸框、闭眼提示叠层；
- 快速前后图切换；
- 星级/颜色/采用状态快捷键；
- 按问题类型筛选；
- 按时间线、事件或覆盖缺口浏览；
- “最佳图与备选图为什么不同”的可验证证据。

### 大任务可用性

复核页直接渲染全部结果和全部故事按钮，没有虚拟化。每次修改也返回并发送完整快照。17 张尚可，1000 张时 DOM、序列化、状态更新和滚动都会有明显风险。

### 可读性与可访问性

大量正文、元数据和按钮使用 6–10px 字号，低于适合桌面长期审片的可读尺寸。焦点样式、键盘导航、模态焦点约束和屏幕阅读器流程也没有专门验证。

## 性能与工程问题

1. 分析循环逐张串行执行：完整渲染 → 人脸检测 → 每只眼分类 → 感知哈希。
2. 相似组搜索是组内两两比较，最坏为 O(n²)。
3. 取消只在两张资产之间检查；单张完整渲染或推理无法中断。
4. 每次快照会克隆全部结果、失败项和人脸，并通过 Tauri 事件发送。
5. 当前 17 张 PNG 小样本几秒完成，但这不能证明 1000 张 RAW/JPEG、包含蒙版和裁剪的任务能达到 5 分钟目标。
6. macOS 模型会话使用 `CoreMLComputeUnits::CPUAndGPU`；关闭的是 ONNX Runtime 的 CPU EP 回退，不能等同于 Core ML 内部“绝不使用 CPU”。当前 UI 的“Core ML GPU/CPU 回退已禁用”表述不够精确。

## 已确认可保留的基础

以下部分实现方向正确，并有单元测试覆盖，建议原样复用：

- 递归扫描与 GIF/TIFF 排除；
- RAW/JPEG 同目录同名配对；
- RAW/JPEG 任一成员存在人工结果时整组保护；
- RAW 组合只写 RAW 对应 `.rrdata`；
- 非 RAW 单文件写自己的 `.rrdata`；
- AI 结果被用户修改或取消后转为人工来源并清除 AI 原因；
- 文件和 sidecar 基线校验；
- 写入前再次检查人工保护；
- 临时文件 + `sync_all` + 原子替换；
- 单项失败不回滚其他成功项；
- 完全离线、本地模型完整性校验；
- 复用现有 GPU 当前渲染状态，包含裁剪、蒙版和调整；
- 失败项和保护项的数据结构；
- 智能选图功能目录与上游主功能的隔离方式。

## 测试覆盖判断

现有 42 个智能选图 Rust 测试全部通过，但它们主要证明数据安全、资产配对、状态枚举和基础数学函数；没有覆盖：

- 关键人物事件导致页面跳转；
- 图片内容矩形与人脸框坐标；
- 不同窗口宽高；
- 相似组召回率；
- 选图准确率；
- 故事覆盖；
- 关键人物身份准确率；
- 1000 张性能；
- Windows DirectML 真机；
- 前端复核快捷工作流。

## 建议的开发边界

继续保持独立功能域开发：

- 保留现有 catalog、metadata ownership、baseline、persistence、render input、preflight；
- 在智能选图功能目录内部重建 viewer、frontend state reducer、analysis feature extraction、grouping/story、scoring contract 和 review workbench；
- 不把新业务逻辑塞入 `App.tsx`、图库主组件或编辑器主流程；
- 只通过现有 feature slot、Tauri command/event 和 `.rrdata` 契约与上游代码连接。

## 尚需验证的 5%

在开始“完整能力”代码实现前，还必须建立以下验收基准：

1. 至少一套人工标注的摄影样本集，覆盖连拍、人像、群像、风光和混合场景。
2. Apple Silicon 低配/中配/高配及 Windows DirectML 三档性能。
3. 1000 张 RAW/JPEG、包含编辑和蒙版的 5 分钟目标。
4. Windows 100%/125%/150% DPI 与最小窗口。
5. 键盘、VoiceOver/Narrator、色弱与低对比度检查。
