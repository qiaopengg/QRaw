# 智能选图问题解决方案与 95% 信心门

日期：2026-07-29

适用范围：当前 QRaw 工作区的智能选图功能域

前置证据：[智能选图二次审计](./audit.md)

## 1. 执行结论

本轮先完成研究、技术刺探和方案冻结；用户确认 GPU 边界后，已进入 M1/M2 的确定性工程实现。

已经达到 95% 以上把握、可以进入实现的部分：

- 前端页面状态与后台任务状态解耦；
- 关键人物图片的自适应显示、缩放、平移、1:1 和准确坐标映射；
- 配置、关键人物、分析、复核页面的桌面响应式布局；
- 当前渲染预览、缩略图缓存、快捷键和虚拟列表的复用方式；
- 按文件夹、拍摄时间、视觉特征分组的管线结构；
- 保留现有 RAW/JPEG 配对、人工保护、基线校验和原子写入。

尚未达到“完整功能可发布”95% 门槛的部分：

- “禁止降级”是否允许少量固定、低成本的 ONNX 图节点留在默认 CPU EP；
- Windows DirectML 真机的模型兼容性和持续吞吐；
- 1000 张真实 RAW/JPEG、包含调整和蒙版时能否在目标低配设备 5 分钟内完成；
- 九种模式、关键人物、拍摄组合、误标红和组内 3–5 张推荐的真实摄影标注集指标。

因此本方案把“可确定的工程修复”和“必须由数据验证的效果能力”分开设 Gate。任何未通过 Gate 的
能力不得以假数据、假原因、固定百分比或静默降级形式进入生产页面。

## 2. 已确认的复用边界

### 2.1 直接复用

| 能力           | 现有位置                                                         | 方案                                                  |
| -------------- | ---------------------------------------------------------------- | ----------------------------------------------------- |
| 当前渲染图片   | `generate_preview_for_path`、`render_current_state`              | 继续复用同一解码、调整、裁剪、蒙版、LUT 和 GPU 渲染链 |
| 高质量预览缓存 | `useProcessStore.previews`                                       | 关键人物和复核检查器共享，不再只显示普通缩略图        |
| 审片缩放交互   | `CullingView.tsx` 的 fit、1:1、点中心缩放、平移和同步视口约定    | 沿用交互和数学约定                                    |
| 大列表         | `react-window` 已用于图库和 CullingView                          | 复核组列表和人物胶片条复用同一依赖                    |
| 拍摄时间       | `ImageFile.exif.DateTimeOriginal`、`get_creation_date_from_path` | catalog 复用现有 EXIF/文件时间读取入口                |
| 快捷键注册     | feature `keyboardActions` 和全局快捷键聚合                       | 智能选图只注册上下文快捷键，不再另建键盘系统          |
| 数据安全       | catalog、metadata ownership、baseline、persistence               | 原样保留，并作为所有新结果写入的唯一出口              |

### 2.2 不能直接复用的部分

`CullingView.tsx` 中的 `CullingPreview` 是私有组件，并与图库打星、标签、悬停和比较状态强耦合；
整个文件超过 1200 行。为了复用它而继续扩大该上游文件，或把智能选图状态注入图库组件，都会违反
本项目“独立开发维护、不污染上游”的边界。

因此新增的查看器应位于 `src/features/smart-culling` 内，但只实现查看器自己的几何和交互：

- 复用 `GeneratePreviewForPath`、`LoadMetadata`、`useProcessStore.previews`；
- 复用项目已有缩放/平移操作方式；
- 不复制任何 RAW 解码、调整、裁剪、蒙版或 LUT 算法；
- 不带入图库的标签编辑、上下文菜单和多选业务。

这不是复制上游业务逻辑，而是在 feature 内建立缺失的、可测试的证据查看端口。

## 3. GPU 与离线模型实测

### 3.1 测试环境

- 设备：Apple M4 Max，32 核 GPU，36 GB 统一内存；
- 运行时：QRaw 当前打包使用的 ONNX Runtime；
- 执行器：CoreML EP、MLProgram、固定输入尺寸、`CPUAndGPU`；
- 测试均使用本地文件，不上传图片，不在运行时下载模型；
- 模型会话按应用生命周期缓存，避免 CoreML 异步销毁和重复编译。

### 3.2 结果

| 模型                      | 用途                 |   体积 | 严格禁止默认 CPU EP | ORT provider profiling                   |     本机热推理 |
| ------------------------- | -------------------- | -----: | ------------------- | ---------------------------------------- | -------------: |
| 当前上游 CLIP 图像分支    | 视觉语义             | 336 MB | 会话创建失败        | 未进入可用会话                           |         不采用 |
| DINOv2 ViT-S/14，固定 224 | 分组、相似度、多样性 |  84 MB | 会话创建失败        | CoreML 子图；默认 EP 只有低成本 `Gather` | 中位数 3.27 ms |
| OpenCV SFace，固定 112    | 人物身份特征         |  37 MB | 会话创建失败        | 默认 EP 仍有 `Flatten/Gemm/BN`           | 中位数 1.55 ms |

DINOv2 首次 CoreML 编译约 35 秒。CoreML 的设备计划显示 438 个操作使用 M4 Max GPU；ONNX
Runtime 节点 profiling 进一步确认默认 EP 只有 `Gather`，符合已接受的低成本白名单方向。

SFace 的 CoreML 设备计划虽然显示卷积等操作使用 GPU，但 ONNX Runtime profiling 发现
`Flatten/Gemm/BatchNormalization` 仍在默认 CPU EP。`Gemm` 和 `BatchNormalization` 不能视为纯
形状整理，因此当前 SFace 不通过 Gate，不得随实现直接接入。

热启动数据不能直接推导 1000 张端到端时间。DINOv2 证明视觉分组候选路径可行；主要性能风险继续
是 RAW 解码、当前渲染、调度和 Windows。

### 3.3 严格模式为何失败

`session.disable_cpu_ep_fallback=1` 的含义是：只要 ONNX Runtime 认为图中仍有节点未被 CoreML EP
接管，整个会话就失败。它不能区分：

- 占主要计算量的卷积、矩阵乘、注意力；
- 常量、形状、索引、输入输出整理等低成本图节点。

实测中，DINOv2 的 CoreML 计算计划记录了 438 个 GPU 操作，而 ONNX Runtime profiling 只发现
低成本 `Gather` 留在默认 EP，但严格会话仍被拒绝。这证明“整张 ONNX 图零默认 EP 节点”与
“模型重计算确实在 GPU”不是同一个判断。SFace 同时证明不能只看 CoreML 设备计划，必须叠加
ONNX Runtime provider profiling 才能阻止高成本 CPU 节点被误放行。

### 3.4 推荐的“不降级”定义

推荐把生产约束明确为：

1. 不允许切换到更小、能力不完整或不同输出语义的备用模型；
2. 不允许核心模型整体落到 CPU；
3. 不允许预检失败后继续分析；
4. 核心卷积、矩阵乘、注意力和其他高成本算子必须由 CoreML/DirectML 执行；
5. 只允许经过版本锁定和逐模型审计的低成本图节点留在默认 EP；
6. 安装包中的每个模型都必须通过固定输入、SHA、输入输出契约、设备计算计划和吞吐 Gate；
7. 设备或驱动不满足 Gate 时禁用智能选图，不影响 QRaw 其他功能；
8. UI 显示“已验证 GPU 加速路径”，不再声称“CPU 完全禁用”。

该定义没有降低模型质量，也不是发生错误后的 CPU 回退。它把门槛从无法准确描述执行事实的
“每个图节点必须属于同一 EP”，改为可审计的“重计算必须在目标 GPU，且端到端性能与输出通过验证”。

如果产品坚持“ONNX 图的每一个节点都不能由默认 CPU EP 执行”，当前三个标准模型均不可用，必须走
平台专用模型转换和运行时集成：macOS 原生 Core ML 模型、Windows 专用 DirectML ONNX，并分别维护
打包、契约和测试。这会显著增加安装资源、开发量和双平台行为差异，当前不建议直接进入实现。

## 4. 前端状态解决方案

### 4.1 单一职责

后台任务状态只描述任务事实：

```text
idle -> scanning -> analyzing -> organizing -> readyForReview
     -> confirming -> writing -> completed
```

前端 `workspaceScreen` 只描述用户当前正在看的页面：

```text
setup | people | analysis | review | write | unsupported
```

事件监听器只更新 `snapshot`。只有下列状态可以自动导航：

- `analyzing` 首次开始：进入分析页；
- `readyForReview` 首次完成：进入复核页；
- `completed`：进入完成页；
- `unsupported`：进入设备说明页。

`configuring`、人物检测结果、复核编辑回执都不得改变用户当前页面。这样可消除
`detectPeople -> configuring -> setup` 的阻断问题。

### 4.2 实现形态

- 把屏幕迁移写成纯 reducer；
- `runSmartCullingCommand(..., preserveScreen)` 不再与事件监听器各维护一套规则；
- 为人物检测、分析完成、复核更新、写入完成建立状态迁移测试；
- 检测失败只清理本次检测结果，不清理已经选中的关键人物；
- 离开任务或完全取消时才清理任务级人物特征。

## 5. 统一图片与坐标契约

### 5.1 后端返回

人物检测响应应与前端展示图绑定，至少包含：

```text
path
previewRevision
sourceWidth
sourceHeight
previewWidth
previewHeight
faces[].bboxNormalized
faces[].landmarksNormalized
```

`previewRevision` 由原文件基线、sidecar/调整摘要和渲染版本组成。前端展示的预览与后端检测使用同一
revision；不一致时不显示人脸框并重新请求，禁止把旧坐标套到新画面。

### 5.2 `PhotoEvidenceViewport`

在智能选图 feature 内新增独立查看器，职责限定为：

- `ResizeObserver` 获取实际容器尺寸；
- 根据图片宽高计算 `containRect`，人脸框定位到内容矩形而不是容器；
- 维护 fit、1:1、缩放、平移；
- 滚轮/触控板以指针位置为中心缩放；
- 拖动平移，双击在 fit 与 1:1 间切换；
- 保持人脸框与图片使用同一变换矩阵；
- 支持上一张/下一张、放大/缩小、fit/1:1 键盘操作；
- 复核比较时可选同步视口。

纯几何函数必须覆盖：

- 横图放入竖容器；
- 竖图放入横容器；
- 相同宽高比；
- 100%、125%、150% 缩放；
- resize 后保留或约束 pan；
- bbox 靠近四边与最小人脸框。

## 6. 桌面响应式布局

响应式判断基于智能选图内容区宽度，不基于整个浏览器窗口宽度。移除 `.sc-page` 的固定
`min-width: 960px`。

| 内容区宽度   | 布局                                             |
| ------------ | ------------------------------------------------ |
| `>= 1120px`  | 文件/故事导航 + 主工作区 + 检查器三栏            |
| `760–1119px` | 左侧导航可收起，检查器为抽屉，主工作区保持最大   |
| `< 760px`    | 单主栏；导航和检查器均为抽屉；底部主操作固定可见 |

配置页、人物页、分析页和复核页使用同一壳层和断点。最小可用目标不是塞下三栏，而是保证：

- 当前主任务始终可操作；
- 图片按可用区域自适应；
- 主按钮始终可见；
- 不出现页面级水平滚动；
- 侧面信息通过抽屉访问；
- 触控目标不小于 32px，正文不再使用 6–10px 字号。

验收视口至少覆盖：应用窗口 961×601、1280×720、1404×768，以及 100%、125%、150% 系统缩放。

## 7. 分组、故事和选图算法

### 7.1 特征管线

每个资产只分析一次，RAW/JPEG 配对共享同一结果：

1. `Catalog`：文件夹、拍摄时间、文件序号、资产组合、人工保护、基线；
2. `RenderFast`：完整当前渲染状态的受控尺寸图；
3. `Technical`：主体/人脸区域清晰度、曝光裁切、闭眼、检测可靠性；
4. `Embedding`：DINOv2 视觉特征，用于相似度和多样性，不直接伪装成审美分；
5. `Identity`：YuNet 五点对齐后使用通过 GPU Gate 的身份模型生成人物特征，只在人物适用模式和当前
   任务内保存；当前 SFace 候选未通过 Gate，不接入生产；
6. `RenderFine`：只对候选最佳、边界样本、人物小脸和疑似淘汰图进行更高分辨率复查。

不得继续用人脸裁剪 pHash 代表人物身份，也不得用横竖构图猜测风光/产品模式。

### 7.2 相似组

每个子文件夹独立处理：

1. 先按 `DateTimeOriginal` 和文件序号切分拍摄段；
2. 在时间邻域内按 DINOv2 余弦相似度、人脸身份集合和构图变化建边；
3. 使用 anchor/complete-link 约束，避免 A 像 B、B 像 C 导致 A 与 C 被传递合并；
4. 缺少 EXIF 时回退到文件创建时间和文件序号，并把不确定性写入证据；
5. 单张保留为单张组，但不把它伪称为一个“故事”。

“故事段落”只表示时间连续、视觉连续且人物/场景集合稳定的拍摄段。没有经过语义验证前，不使用
“仪式、关键事件、高潮”等虚构描述。

### 7.3 组内推荐

- 组小于 3 张：按实际数量保留；
- 组大于等于 3 张：默认推荐 3 张；
- 只有姿态、表情、构图或关键人物覆盖存在有效差异时增加到 4–5 张；
- 先过滤确定性技术失败，再用质量、人物优先级和多样性选代表图；
- 低置信度只标黄，禁止标红；
- 受保护的包围曝光、全景、焦点堆栈等拍摄组合不自动淘汰成员；
- 组合识别不确定时整组标黄，交给用户复核。

### 7.4 原因和置信度

原因必须来自可查看证据，例如：

- “关键人物 1 在本图睁眼，组内另一张闭眼”；
- “主体区域清晰度高于组内中位数”；
- “构图与已选图重复，但没有新增人物或姿态覆盖”。

没有标注集校准前，UI 只显示“高 / 中 / 低可信度”，内部保留原始分数和证据。不得继续把距离
0.5 的固定公式显示成 70%、96% 等统计百分比。只有经过独立验证集校准后才允许显示百分比。

## 8. 九种模式

九种模式不需要九个模型，但每种模式必须是“信号是否适用 + 信号权重 + 保护规则”的可验证策略：

- 人像/群像：人脸清晰、睁眼、关键人物、表情和姿态多样性；
- 环境人像/纪实：人物与环境覆盖并重，降低中心构图偏置；
- 风光/建筑：全局和局部细节、曝光、重复构图；不使用人脸缺失作为模式证据；
- 野生动物：主体检测和眼部能力未接入前不得宣称完整支持；
- 星空：星点、拖线和高 ISO 噪声能力未接入前不得宣称完整支持；
- 产品：主体边缘、背景和重复角度能力未接入前不得宣称完整支持；
- 自动：使用已验证的场景路由；路由不确定时使用混合策略并标示模式不确定。

没有真实样片证明收益的模式保留在目标范围，但不能用现有固定权重冒充已经完成。

## 9. 专业复核工作台

### 9.1 必需能力

- 文件夹、拍摄段、相似组三级导航；
- 虚拟化组列表，只渲染可见组；
- 同组 2–4 图比较；
- fit、1:1、同步缩放和平移；
- 人脸框、闭眼、主体/对焦证据叠层开关；
- 最佳图和备选图之间的证据差异；
- 采用、星级、颜色标签快捷键；
- 按闭眼、虚焦、过曝/欠曝、重复、低可信度、失败项筛选；
- 小窗口下检查器和导航变为抽屉；
- 已完成页继续显示 AI/人工来源和 AI 原因；
- 用户修改 AI 星级/标签时转为人工来源并清除 AI 原因，沿用现有保护逻辑。

### 9.2 大任务数据流

- 后台进度事件只发送增量和计数；
- 完整快照由显式状态查询获取；
- 复核修改只回传受影响结果，不广播 1000 张完整结果；
- 结果、特征和预览按文件基线 + sidecar revision + 模型版本缓存；
- 取消标记在各阶段和 GPU 批次边界检查，2 秒内停止提交新的重任务。

## 10. 性能结构

推荐采用有界流水线：

```text
扫描/基线
  -> 有界解码与当前渲染
  -> 固定尺寸 GPU 推理队列
  -> CPU 轻量统计
  -> 文件夹内时间/视觉分组
  -> 候选精查
  -> 结果增量
```

- CoreML/DirectML 会话按应用生命周期缓存；
- 固定输入尺寸，避免每张图重新编译；
- GPU `Run` 使用串行或小批次队列；DirectML 同一会话不并发 `Run`；
- 解码和文件读取有界并发，不按 CPU 核数无界展开；
- 分组只在时间邻域内搜索，避免全目录 O(n²)；
- 分析后端直接消费内存中的当前渲染图，不经 JPEG 编码和前端 IPC；
- 缓存命中不得绕过 sidecar/文件基线校验。

发布基准必须记录扫描、解码、渲染、各模型、精查、分组、写入、RSS/显存和取消延迟。单模型热推理
快不等于端到端已达标。

在兼容、许可、效果和资源 Gate 前，不加入依赖或安装包。

## 13. 实施顺序

### M1：确定性 UI 和状态修复

1. 状态 reducer 与人物页跳转回归测试；
2. 统一预览 revision 和图片坐标契约；
3. feature-local 查看器；
4. 人物页缩放、平移、1:1、键盘和精确人脸框；
5. 全生命周期响应式壳层；
6. 复核比较查看器和虚拟化。

完成条件：Mac 三档窗口、三档缩放、人物选择、坐标单测、键盘和生命周期回归通过。

### M2：数据与分组基础

1. catalog 接入现有 EXIF 拍摄时间；
2. 有界分析流水线和增量事件；
3. 文件夹 + 时间段 + 视觉特征分组接口；
4. 证据、可信度等级和原因契约；
5. 保持现有保护/写入模块不变。

完成条件：人工构造时间线与相似度 fixture 的分组、顺序、传递链和缺 EXIF 测试通过。

### M3：GPU 模型 Gate

1. 产品确认“不降级”的技术定义；
2. 固定并随包分发模型；
3. Mac 低/中/高配与 Windows DirectML 真机验证；
4. 计算计划、吞吐、内存/显存、温控后持续性能记录；
5. 不通过则只禁用智能选图。

### M4：效果与性能

1. 冻结合法、可复现的标注集；
2. 调整分组阈值和组内 3–5 张策略；
3. 校准人物误匹配、组合保护、误标红、原因真实性；
4. 50/200/1000 张冷/热缓存基准；
5. 九模式逐项开放，不通过的模式不得伪装完成。

Windows 真机、标注集和 1000 张基准约束，不能靠实现者主观宣布完成。

## 16. 已确认的产品决定

用户已于 2026-07-29 接受以下“不降级”定义：

> 模型、输出语义和分析能力不降级；核心高成本计算必须在经过验证的 CoreML/DirectML GPU 路径；
> 允许经过逐模型审计、固定白名单且不影响质量/时限的低成本 ONNX 图节点由默认 EP 执行；若设备未
> 通过计算计划和端到端性能 Gate，则禁用智能选图，绝不整体回退 CPU 或换低质量模型。

M1/M2 据此开始；M3 继续以逐模型 provider profiling、Mac/Windows 真机和端到端性能 Gate 约束。

## 17. M1/M2 实现检查点

截至 2026-07-29，已经实现并验证：

- 前端页面导航与后台任务状态分离；人物检测回执不再把用户送回配置页；
- feature-local 当前渲染查看器支持 contain、fit、1:1、滚轮缩放、拖动平移和键盘切图；
- 人脸框与实际图片内容矩形共用同一变换，且只在对应路径的当前渲染预览加载后显示；
- 关键人物页和复核页在紧凑窗口下改为单主栏/抽屉，不再依赖固定 960px 页面宽度；
- 复核页提供同组最多四图比较、同步视口、虚拟化相似组列表和高/中/低可信度；
- 缺少 EXIF、文件时间不可靠但文件序号连续的样本会按自然拍摄顺序组织，不再被复制时间拆成大量单张组；
- 真实本地 17 张 PNG 样本从“默认采用 16 张”收敛为 1 个拍摄段、1 个相似组、默认采用 5 张；
- 全程停在复核页，未执行确认写入，正式 `.rrdata` 未被本次 UI 验证修改；
- macOS debug `.app` 构建通过；源码仍只位于智能选图功能域和本次审计目录。

本检查点不代表完整发布 Gate 已通过：

- DINOv2 尚未随包接入；当前分组是时间、文件序号和现有视觉哈希基础，不等于真实摄影相似度已达标；
- 当前 SFace 被拒绝，关键人物跨照片身份匹配仍未达到产品 Gate；
- Windows DirectML、1000 张/5 分钟、复杂拍摄组合和九模式真实效果仍需 M3/M4 证据；
- 当前预览与检测已绑定同一路径，但完整 `previewRevision` 契约仍需和缓存/基线阶段一起补齐。
