# 智能选图需求纠正实施方案

> 状态：实施前技术方案  
> 依据：`docs/需求纠正.md`  
> 目标：在不污染 QRaw 上游业务代码的前提下，纠正关键人物、相似照片分组和复核页信息架构；任何未经验证的能力都不得伪装成可靠 AI 结论。

## 1. 本轮成功标准

本轮代码修改只有同时满足以下条件才可视为完成：

1. 删除故事段落的前后端字段、分组、筛选、文案和 UI，不换名保留隐藏逻辑。
2. 默认复核页变为保留原始宽高比、保持时间阅读顺序、支持大数据量虚拟化的全结果总览。
3. 独立照片不再进入“相似照片对比”主界面；A/B 只在用户主动要求时出现。
4. 规则匹配相似组具有 3～5 张初始入选、其余照片层叠入口、展开后的上下双池和双向移动；疑似受保护
   拍摄组合例外地全部初始保留。
5. 关键人物不再使用人脸裁剪感知哈希；必须先定位具体人脸，再评价该人脸本人。
6. 眼睛、脸部清晰度和人脸曝光均绑定到具体人脸，并且低置信结果进入复核。
7. 表情能力在没有经过真实样片验证前不得生成确定性结论、强理由或自动淘汰。
8. 用户改星级或颜色标签仍转为人工来源、清除 AI 理由并受保护；仅在双池移动不触发人工保护。
9. 身份特征只存在于当前任务内存，不写入 `.rrdata`，任务结束立即清理。
10. 模型推理完全离线，不允许 ONNX Runtime 静默回退到默认 CPU EP；不支持的设备在功能级明确阻止
    启动。Core ML 内部如何在 CPU/GPU 间调度必须单独实测，不以 EP 名称冒充 GPU-only 证据。
11. macOS、Windows、真实多人样片和 1000 张性能中尚未通过的项目必须显式列为发布门禁，不能以“代码已接入”代替验证。

本轮“代码完成”不等于“四维专业效果正式发布”：表情自动评分、身份自动影响推荐、受保护拍摄组合
完整识别、Windows 正式支持和 1000 张性能达标在通过各自门禁前均属于**未完成能力**。本轮可以完成它们
的正确数据边界、候选展示、未知状态、风险缓释和预检，但最终报告必须逐项标出未完成，不能合并成
“智能选图已全部达到专业效果”。

## 2. 自查中最没有把握的事项

### 2.1 关键人物身份模型能否满足严格 GPU 路径

原实现用人脸裁剪感知哈希匹配身份。它不能稳定处理姿态、表情和光线变化，必须替换为人脸特征模型。
不确定点不是“ONNX 能否加载”，而是模型完整计算图能否在 Core ML 和 DirectML 上运行且不回退 CPU。

### 2.2 技术性表情是否已有可信实现

现有模型只有 YuNet 人脸检测和 OCEC 眼睛状态，缺少嘴部动作、说话过渡和表情稳定信号。通用七分类
情绪模型不能回答“这一帧是否处于技术性表情过渡”，也不应输出敏感或主观情绪标签。

### 2.3 相似照片分组是否会继续误收随机照片

现有逻辑在时间、文件序列或宽松感知哈希条件下可能建立组，并把单张照片包装为“对比”。需要确认
哪些信号能证明照片可以互相竞争，且当证据不足时必须宁可拆散，不可误分组。

### 2.4 “瀑布流”、时间顺序和虚拟化能否同时成立

传统最短列瀑布流会改变跨列视觉顺序，与摄影师按时间阅读和键盘顺序冲突。项目已有
`react-window`，但没有 masonry 虚拟化依赖；不能为这个问题引入第二套列表和缓存架构。

### 2.5 95% 把握的含义

必须区分两件事：

- **实施把握**：对代码边界、数据流、UI 状态、模型契约和可验证行为有至少 95% 把握，可以安全开始编码。
- **效果发布把握**：对身份召回、表情、Windows GPU、真实样片 Top-K 和 1000 张性能达到发布阈值有至少
  95% 把握。

本方案可以在编码前达到前者。后者必须依赖 Windows 真机和独立真实样片验证，当前不能诚实宣称已达到。
解决方法不是降低标准，而是把未验证能力关在发布门禁之后，并让未知结果进入人工复核。

## 3. 已完成的研究与证据

### 3.1 现有代码复用边界

可以直接复用：

- `infrastructure/catalog.rs` 的资产目录和 RAW/JPEG 资产规则；
- `infrastructure/baseline.rs`、`persistence.rs` 的人工保护、基线校验和 `.rrdata` 写入；
- `infrastructure/render_input.rs` 的当前渲染状态输入；
- `PhotoEvidenceViewport` 的原图比例、缩放和拖拽；
- `useRenderedPreview` 的高质量预览缓存；
- `ReviewInspector` 的侧边检查器；
- `ReviewCompareWorkspace` 的缩放、拖拽和 A/B 基础能力；
- 现有星级、颜色标签控件；
- 已安装的 `react-window`。

不能继续复用：

- `runner.rs` 中以图像哈希匹配关键人物的身份逻辑；
- `grouping.rs` 的故事段落索引和宽松相似组判定；
- `ReviewWorkbench` 中常驻大图/A-B 工作区；
- `ReviewQueueNavigation` 的故事段落导航；
- 任何用“包含关键人物”直接提高照片质量结论的评分。

### 3.2 身份模型验证

候选模型采用 OpenCV Zoo 的 SFace：

- 上游许可证：Apache-2.0，可随安装包分发，但仍需写入第三方声明；
- 原始模型 SHA-256：
  `0ba9fbfa01b5270c96627c4ef784da859931e02f04419c829e83484087c34e79`；
- 输入：`1 × 3 × 112 × 112`；
- 输出：128 维身份特征；
- 上游给出的 LFW 准确率为 0.9940，官方余弦阈值为 0.363；该数据只能证明模型基准能力，不能替代
  QRaw 真实多人样片验证。

原始模型的末端 BatchNorm、Gemm 会导致本机 Core ML 严格模式拒绝。研究阶段进行了等价图变换：

1. 将 Gemm 前后的 BatchNorm 参数解析折叠；
2. 将最终 Gemm 等价改写为 `7 × 7 Conv`，直接输出包含同样 128 个值的 `1 × 128 × 1 × 1` 张量；
   项目实际绑定的 Core ML MLProgram 路径不支持独立 Flatten，因此运行时按连续 128 值读取；
3. 显式声明零 padding、单位 stride、单位 dilation 和单 group，以兼容项目实际绑定的
   ONNX Runtime/Core ML 编译器；
4. 保留相同输入预处理和 128 维输出语义；
5. 转换模型 SHA-256：
   `3e4a66d8a95745ce8b972e78d1330918db04bdb8ef4a81d02088c50aa8d55a15`。

本机随机输入对照结果：

- 最大绝对误差：`7.748604e-07`；
- 平均绝对误差：`1.7541606e-07`；
- 输出余弦一致度：`0.9999999`。

补齐显式 Conv 属性后，相对上一份等价转换模型的随机输入对照结果为最大/平均绝对误差 `0.0`、输出
余弦一致度约 `1.0000001`；这一步只补充 ONNX 默认属性，不改变计算结果。

在 `session.disable_cpu_ep_fallback=1`、Core ML MLProgram 静态模式下，转换模型能创建会话并完成推理；
原始模型不能。研究环境中的热推理中位数约为 0.727 ms，此数值不代表完整照片流水线性能，也不能
证明 Core ML provider 内部没有使用 CPU。

一次性严格 provider 诊断在完成最终模型推理后，测试进程退出阶段曾触发 Core ML/ONNX Runtime 原生
异步清理的 `mutex lock failed`。正式应用沿用项目已有的 `OnceCell` 生命周期持有推理会话，打包客户端
中的预检和完整分析均已成功；该现象不影响本轮推理结果，但应用退出稳定性仍必须作为发布回归项，
不能把这次一次性诊断描述为“进程全生命周期干净通过”。

结论：macOS 已证明完整模型图可由 Core ML EP 接管且没有回退 ONNX Runtime 默认 CPU EP；尚未通过
Instruments 或等价工具测量 Core ML 内部 CPU/GPU 调度，因此不称为 GPU-only。Windows DirectML 必须由
正式预检在 Windows 候选设备逐模型执行完整图冒烟测试；在完成真机记录前，不宣称 Windows 已验证。

生产仓库只加入一份经转换的运行时模型，避免安装包重复增加约 37 MB。审计材料同时记录：

- 经转换的模型；
- 原始模型的官方来源、Apache-2.0 许可证、修改声明和两个 SHA-256；
- 一次性转换步骤、工具版本、图变换说明和上述数值等价报告；
- 输入输出契约、完整性和真实推理冒烟测试。

本轮不把原始模型放入 Tauri `resources`，不把原/转换双模型等价检查写成常规 Rust 测试，也不新增
Python/ONNX 项目依赖。运行时只验证转换模型 SHA、契约和真实推理。若后续决定把转换工具纳入仓库，
必须另行说明其开发依赖并取得批准。

### 3.3 表情模型结论

OpenCV Zoo 的通用表情识别模型只输出七类情绪。它不能可靠区分说话中间帧、笑容形成过程和符合
拍摄意图的自然互动，因此不作为本轮自动评分依据。

本轮采用以下诚实门禁：

- 数据结构保留 `expression`、置信度和未知原因；
- 没有经过许可、双平台 GPU 验证和真实样片验证的面部动作模型时，输出
  `unknown / model_unavailable`；
- 表情未知不扣分、不成为淘汰理由，也不伪造“表情自然”；
- UI 显示“表情状态待人工确认”，而不是情绪标签；
- 眼睛状态不能冒充完整表情能力。

后续若引入表情模型，必须独立经过许可证、Core ML、DirectML、真实样片一致性和偏差验证，再通过能力
开关加入低权重相对排序。本轮不新增未经证明的表情依赖。

### 3.4 复核总览布局结论

`需求纠正.md` 同时要求“瀑布流”和“跨列视觉填充不能破坏时间顺序”。传统最短列 masonry 无法稳定
满足后者。因此本轮把该页面的“瀑布流”落实为**按行的顺序型照片墙（justified rows，非 masonry）**：

1. 使用结果已有的宽高预先计算每一行的卡片宽度；
2. 每张照片保持原始宽高比、不裁剪；
3. 行内和行间均严格保持数据、DOM、键盘和时间顺序；
4. 使用现有 `react-window` 按行虚拟化；
5. 卡片只使用现有缩略图；可见行通过项目已有 `requestThumbnails → update_thumbnail_queue →
thumbnail-generated → useProcessStore.thumbnails` 链路按需请求、去重，侧边栏和 A/B 才加载高质量预览；
6. 宽度变化时重新计算行布局，但通过照片 ID 恢复锚点和滚动位置；
7. 横图、竖图、方图都由已知宽高先占位，异步图片加载不改变布局。

它保留需求所说的摄影照片墙密度和原始比例，同时优先满足同一需求中更明确的时间线、DOM、键盘和
屏幕阅读器顺序约束，并且无需新增依赖。后续 UI 和文案统一称“照片墙/全部结果”，不向用户暴露
“masonry”术语。

## 4. 最终解决方案

### 4.1 数据与分析流水线

每个 CatalogAsset 的主分析只执行一次当前渲染和一次 YuNet 检测。内部 `FaceAnalysis` 与前端
`FaceEvidenceDto` 分层：身份向量只存在于前者且不可序列化；前端只得到可展示证据。每个具体人脸
产生以下任务内数据：

- 人脸序号、边界框、五点关键点；
- 左眼和右眼各自的状态、置信度和未知原因；
- 人脸与双眼局部清晰度、有效像素和置信度；
- 人脸局部曝光、通道裁切风险和置信度；
- 表情状态、置信度和未知原因；
- 身份特征（仅任务内存，不序列化）；
- 每位关键人物的优先级、余弦相似度、匹配置信度、是否允许自动评分和未知原因。

`ReviewResult` 的纠正后稳定契约为：

- 删除 `story`；
- 增加 `groupKind: similar | single | reviewOnly`、文件夹内稳定 `groupIndex`、`groupRank`；
- 增加不可变 `aiInitiallyAdopted` 和可变 `adopted`；
- `reviewOnly` 是疑似受保护拍摄组合的唯一状态，不再与另一个 safety 字段组合，避免非法状态；同时
  携带组合风险原因代码；
- `faces` 只包含 `FaceEvidenceDto`（归一化 bbox、五点、左右眼、局部清晰度/曝光、表达状态）；
- `keyPersonEvidence` 只包含 priority、faceIndex、候选/可靠/冲突状态、相似度区间、是否允许自动评分和
  该人物在当前相似组内的表现排名；
- 128 维 embedding 只存在于 Rust `FaceAnalysis`，没有 Serialize，不进入 snapshot 或 `.rrdata`。

关键人物采用两阶段处理：

1. 用户保存的仍是现有 `samplePath + normalized bbox + priority`，不把身份向量写入前端状态。
2. 主循环先完成全部 CatalogAsset 的单次渲染、检测和身份特征，再用 `samplePath` 匹配 primary/member：
   如果参考路径就是已分析的 primary，直接在缓存分析结果中按 bbox IoU 找回，不重复渲染。
3. 如果参考路径是 RAW/JPEG 资产对中的非 primary member，或不在主分析结果中，则按 `samplePath` 放入
   有上限的 reference cache，整项任务对同一路径最多额外渲染/检测一次；这是参考样本渲染，不是对
   primary asset 重复评分，数量不超过用户选择的关键人物参考路径数。
4. 参考脸要求 IoU ≥ 0.50、YuNet 检测分 ≥ 0.60、五点均有限且双眼间距达到最小有效像素；否则该参考
   明确标记 `reference_face_not_reacquired`，不猜测邻近人脸。
5. 按 OpenCV SFace 官方实现，用 YuNet 五点顺序
   `右眼、左眼、鼻尖、右嘴角、左嘴角` 做相似变换，对齐到 112 × 112 模板：
   `(38.2946,51.6963)、(73.5318,51.5014)、(56.0252,71.7366)、
(41.5493,92.3655)、(70.7299,92.2041)`。
6. `DynamicImage` 已是 RGB，因此按 `float32 NCHW RGB 0..255` 输入（等价于 OpenCV 对 BGR 源执行
   `blobFromImage(..., swapRB=true)`）；输出 128 维后做 L2 归一化，余弦相似度只比较有限且非零向量。
7. 在全部照片的检测人脸中生成候选相似度；同一张照片内对“关键人物 × 检测脸”矩阵做带 dummy
   `unknown` 节点的最大权重二分匹配，保证一人一脸、 一脸一人。身份相似度决定匹配，人物优先级不得
   扭曲身份分配，只在后续表现合成时使用。
8. 每个 reference 的歧义间隔定义为该 reference 在同一照片中第一、第二候选的余弦差；低于门禁或
   两个 reference 竞争同一张脸时输出 `identity_ambiguous`，不强行分配。
9. 匹配完成后只评价分配到的那张脸；非关键人物的闭眼、清晰度或曝光不得写成关键人物结论。

身份阈值不写成永远正确的魔法数：

- 官方 0.363 仅作为宽召回参考；
- 第一版把 `0.363` 仅用于显示“身份候选”，不把它解释为 QRaw 已验证阈值；
- 真实样片门禁通过前，身份候选的 `autoScoreEligible` 固定为 `false`。系统可以展示候选脸、相似度区间
  和具体人脸技术指标，但不得让身份结果改变星级、颜色标签、入选/未入选或生成确定性身份理由；
- 通过独立样片校准后，才配置更高的自动评分阈值、同图第一/第二候选间隔、最小脸部尺寸和质量门禁；
  这些值集中在智能选图私有策略模块并带版本，不散落为魔法数；
- 未通过门禁或边界结果一律 `identity_uncertain`，只进入人工复核，不自动否定照片；
- 多位关键人物按用户选择顺序加权，但任何人的“出现”本身都不加质量分。

评分按“先可比较、再相对排名”执行：

1. 先分文件夹和规则匹配相似组；
2. 独立照片只生成自身技术质量和待确认信息，不制造组内排名；
3. 相似组内可以展示关键人物候选脸的眼睛、局部清晰度和局部曝光相对排序；真实身份门禁通过前不让
   该排序自动改变推荐；
4. 表情在能力门禁关闭时保持未知；
5. 有可靠差异时生成 3～5 张初始推荐；证据不足时保留更多并标记待确认；
6. 当前允许的原因必须绑定对象和证据，例如“疑似第一关键人物：双眼状态明确，脸部清晰度本组第 2；
   身份尚待确认”；只有身份发布门禁通过后才能去掉“疑似/待确认”；
7. 禁止输出“包含关键人物”“综合最佳”“表情自然”等没有当前证据支撑的理由。

### 4.2 相似照片分组

删除 `story_index` 和 45 秒故事时间片。相似组只在同一文件夹内建立，并采用“误合并优先避免”：

- RAW/JPEG 同资产配对仍视为一张资产；
- 感知哈希统一使用生产配置的 256 bit；所有距离先除以 bit 数得到归一化距离，测试不得再用 64 bit
  假数据验证 256 bit 阈值；
- 有可靠 EXIF 时间时，候选必须同时满足：相邻时间差 ≤ 2 秒、文件序列差 ≤ 2、相对首张和相对前一张
  的归一化哈希距离均 ≤ 0.18；
- 没有可靠 EXIF 时间时，候选必须同时满足：存在文件序列、序列差 ≤ 1、相对首张和相对前一张的
  归一化哈希距离均 ≤ 0.12；文件修改时间不作为拍摄时间替代；
- 任一条件失败即从当前组断开；组内至少 2 张才是相似组，否则是独立照片；
- 序列连续不能单独覆盖视觉剧变，锚点约束阻止链式漂移；
- 低可信或只有一张时输出独立照片，不显示“对比”；
- 所有组在默认总览中保持拍摄时间顺序和组内相邻。

当前代码**不存在**可靠的 HDR、全景、景深合成、延时或堆栈识别，不能写成“沿用现有保护”。本轮
增加的只是保守安全门禁：

- 全景和延时通常会因严格视觉/时间门禁拆为独立照片；
- 对已成组照片计算曝光与局部清晰度跨度；明显曝光包围或焦点跨度标记为
  `captureCombinationSuspected / groupKind=reviewOnly`；
- `reviewOnly` 组的 `recommendedCount=groupSize`，组内每张照片初始均为
  `aiInitiallyAdopted=true / adopted=true`，不进入普通 3～5 张淘汰双池；
- UI 显示“疑似拍摄组合，已全部保留待确认”。用户仍可主动移出个别照片，但系统不能先替用户丢项；
- `reviewOnly` 组不产生红色淘汰、不把任何照片解释为较差；
- 在专用组合识别通过真实数据验证前，普通组的未入选照片也只使用黄色待确认，不生成红色强否定。

这些门禁降低误伤后果，但不等于已经识别全部受保护拍摄组合。完整组合识别保留为发布门禁，最终报告
必须明确“尚未完成”，不得宣称本轮已满足该项专业效果。

当前感知哈希只承担保守的构图近似门禁，不再承担人物身份。若真实样片表明它仍无法满足误合并门槛，
再单独评估经过 GPU 验证的视觉嵌入模型；本轮不把未经验证的新模型叠加进主链路。

### 4.3 复核页信息架构

默认层级：

```text
全任务顺序型比例流
  ├─ 点击照片 → 右侧检查器
  ├─ 点击规则匹配相似组标识 → 该组双池
  └─ 主动指定 A/B → 按需对比层
```

#### 全任务总览

- 左侧只保留文件夹和复核队列，不再出现故事段落；
- 主区默认显示全部具体照片；
- 提供“全部、AI 入选、AI 未入选、待确认”筛选；
- 当任务配置了关键人物时，增加“关键人物 N 候选”轻量筛选；每个相似组内按该人物的表现排名，
  不把不同文件夹或不同组放到同一淘汰排名中；可靠候选和身份不确定候选分区显示；
- 卡片显示缩略图、文件名、来源、入选状态、星级、标签、理由摘要和组标识；
- 独立照片明确显示“独立照片”，没有“对比”或虚构排名；
- 点击照片只更新当前选中项和现有侧边检查器，不离开总览；
- `LibraryFeatureContext` 增加通用、可选的 `onRequestThumbnails` 透传点，`LibraryView` 只透传现有
  `requestThumbnails`，不包含智能选图业务。虚拟列表在 `onRowsRendered` 中仅请求可见及 overscan 行里
  缺失的路径，沿用全局去重、500 项队列上限和 `thumbnail-generated` 监听；卡片不得调用
  `useRenderedPreview`。

#### 相似组双池

- 初始入选为系统推荐的 3～5 张，少于 3 张按实际数量；
- 折叠时显示入选照片和可点击、可聚焦的“其余 N 张”层叠卡片；
- 展开后上方入选池、下方待选池；
- 两池都能查看照片并通过按钮双向移动，拖拽不是唯一方式；
- 后端返回不可变 `aiInitiallyAdopted`，与当前 `adopted` 分离，才能实现“采用本组初始建议”；恢复操作
  是一组 `metadataEdited=false` 的批量采用状态变更；
- 两池移动只改变任务采用状态，不改星级、标签、来源和人工保护；
- 返回总览后状态立即同步。

#### 按需 A/B

- 复用现有 `ReviewCompareWorkspace` 的决策控件和 `PhotoEvidenceViewport` 的查看能力，但把 A/B 从内部
  隐式状态改为受控 `aResultId / bResultId`；总览持有 ID、来源入口、原焦点和滚动锚点；
- 只允许同一规则匹配相似组的照片形成结果判定型 A/B；
- 从任意池或侧边栏设 A/B；
- 对比层是临时覆盖层，不替换总览状态；
- 关闭后恢复原筛选、滚动锚点、侧边栏照片和焦点；
- 保留交换、同步/独立缩放、拖拽、Fit、1:1、横竖图自适应；
- 普通同步仍以各自原图归一化坐标工作；人脸对齐不是复用普通同步；
- `PhotoEvidenceViewport` 增加显式 `focusRegion` 能力：利用两边同一 priority 的可靠人脸 bbox，分别计算
  让人脸中心位于视口中心、脸框占据相同目标比例的 zoom 和 pan，因此横图与竖图使用不同 viewState；
- 关键人物对齐仅在两张图都存在同一 priority 的可靠身份匹配时启用，否则明确禁用并说明原因；
- dialog 关闭时由总览恢复原筛选、滚动锚点、侧边栏选中项和键盘焦点，不依赖组件恰好未卸载。

### 4.4 状态与持久化

- 分析产生的星级、颜色标签、来源和可展示理由仍通过现有协调器写入；
- 用户手动改星级或标签时，复用现有人工保护逻辑；
- `adopted` 是当前智能选图任务的复核状态，不自动转成人工来源；
- 将现有 `ReviewChange.edited` 拆为明确语义：`metadataEdited` 只表示星级/颜色标签被用户修改；
  `modeChanged` 只表示任务内拍摄类型纠正。前者转人工并清除 AI 理由，后者不改变星级/标签来源和人工
  保护；
- 当前会话没有保留完整候选重新评分上下文，因此模式纠正不伪造即时重评分：更新组内 mode，并把
  模式相关理由替换为“已按纠正模式标记，技术结论待复核”。若以后保留可重算证据，再单独实现重评分；
- 身份特征、人脸匹配中间值、A/B、池展开状态和滚动状态均不写入 `.rrdata`；
- 最终确认只写任务最终采用且通过基线校验的结果；失败项继续逐项列出。

## 6. 测试与验收

### 6.1 自动化

Rust 常规自动化至少增加或更新：

- 模型 SHA、输入输出契约、严格 GPU 会话和真实推理冒烟；
- SFace 对齐模板、颜色/范围、L2 归一化和有限向量测试；
- 参考 bbox 重新找脸的 IoU/置信失败路径；
- 合成相似度矩阵的最大权重独占匹配、冲突和 unknown 门禁；
- 多人独占匹配，不把非关键人物状态写给关键人物；
- 左右眼分别输出，未知不默认睁眼；
- 局部清晰度和曝光只使用对应人脸区域；
- 表情门禁关闭时不影响评分、不生成虚假理由；
- 与生产一致的 256 bit 哈希：随机照片不分组、可靠连拍成组、同时间同序号但视觉不同必须拆组、
  相似画面跨长时间拆组、链式漂移被 anchor 拦截、单张不显示组；
- 无 story 字段且排序保持时间和组内相邻；
- 3～5 张初始推荐与当前采用状态分离；
- 人工保护和 `.rrdata` 不写身份特征的回归测试。

原/转换 SFace 数值等价属于一次性模型审计报告，不列为依赖未提交原始模型的常规测试。同一人物跨角度、
表情、遮挡和真实多人匹配属于外部真实样片门禁，不伪装成仓库内合成单测。

前端至少通过：

- `npm run typecheck`
- `npm run lint`
- `npm run i18n:check`
- `npm run build`

Rust 必须从包含 `rust-toolchain.toml` 的目录运行仓库现有命令：

- `cd src-tauri && cargo test features::smart_culling`
- `cd src-tauri && cargo check`

### 6.3 发布门禁

以下项目未完成前，即使代码和构建通过，也不能宣称相应效果已正式完成：

1. Windows 候选设备上的 DirectML 完整图严格冒烟；
2. 独立真实多人连续拍摄验证集；
3. 预先书面确定身份召回、误匹配、眼睛、清晰度、曝光和 Top-K 阈值；
4. 表情动作模型及其双平台、样片和偏差验证；
5. 1000 张约 5 分钟目标、峰值内存和失败率实测。
6. HDR、全景、景深合成、延时和堆栈等受保护拍摄组合的可靠识别。
7. 独立随机照片与真实连拍验证集上的相似组误合并率、漏分率；阈值必须在独立保留集验证。
8. macOS 应用退出时 Core ML/ONNX Runtime 原生异步清理的稳定性回归。

未过门禁时的产品行为：

- 平台模型预检失败：功能级阻止启动并说明；
- 身份或单项结果低置信：标记待确认，不做强结论；
- 表情模型未验证：表情状态待人工确认；
- 身份真实样片门禁未验证：只显示“疑似关键人物候选”，不影响自动推荐；
- 相似组真实样片门禁未验证：UI 称“规则匹配相似组/建议复核”，未入选只使用黄色待确认，不宣称
  分组效果已发布达标；
- 疑似受保护拍摄组合：整组 review-only，不产生红色否定；
- 性能没有达标：记录阶段耗时并继续优化，不能减少分析维度来伪造达标。
