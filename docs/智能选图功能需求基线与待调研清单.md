## 1. 项目级强制边界

### 1.1 上游与二开必须独立维护

- 上游为 CyberTimon/RapidRAW。
- QRaw 的智能选图属于二开功能，必须采用外挂式 feature 接入。
- 禁止把智能选图业务实现散落写入上游组件、公共工具或 Rust 核心模块。
- 前端主体只能维护在 src/features/smart-culling。
- Rust 主体只能维护在 src-tauri/src/features/smart_culling。
- 上游文件只允许存在统一注册、通用插槽、通用契约和必要透传。
- 后续同步上游更新时，应优先保持上游提交原貌，二开变化继续由独立 feature 承担。

- 智能选图中部页面必须主动适应宿主留给它的实际宽度。

## 2. 产品目标

智能选图不是简单检测图片是否清晰，也不是为全部题材套用同一套评分公式。

其目标是：

> 用户选择一种拍摄类型后，系统使用该类型对应的证据、优先级和组内比较逻辑，对高匹配、高质量
> 照片给出较高星级，对低匹配或明显较弱照片给出较低星级，从而降低摄影师筛选大量照片的时间。

必须遵守以下原则：

- 每次任务只选择一种拍摄模式；
- 不同模式的主评分证据和优先级必须真正不同；
- 相同证据可以复用，但不能只换一组表面权重就宣称支持不同模式；
- 打星应尽量在同一场景、连拍或相似照片组内进行相对比较；
- 无法可靠判断时不得伪造确定性结论；
- 所有自动能力都服从人工评分保护这一最高安全底线。

## 3. 已确认的用户操作范围

### 3.1 文件夹范围

- 智能选图只处理用户当前选中并展开的文件夹。
- 处理范围是该文件夹当前层级的全部支持图片。
- 不进入任何子文件夹。
- 不递归分析更深层级。
- 如果用户希望处理另一个文件夹，需要切换并展开该文件夹后重新启动任务。
- 当前层级中的受保护资产保持原结果，不允许系统修改。

这里的“全部图片”表示当前层级的任务范围，不代表可以覆盖人工锁定结果，也不代表已经确认所有
图片格式。具体支持格式仍需单独冻结。

### 3.2 拍摄模式

每次任务必须且只能选择以下一种模式：

1. 自动；
2. 风光；
3. 人像；
4. 环境人像；
5. 群像；
6. 街拍；
7. 动物；
8. 建筑；
9. 产品；
10. 银河。

模式名称可以在中英文界面中使用符合摄影习惯的完整名称，但内部模式身份必须稳定，不能因文案变化
改变数据语义。

### 3.3 最小操作路径

本轮确认的最小路径为：

1. 用户在左侧来源栏选中并展开目标文件夹；
2. 用户点击智能选图图标；
3. 中间区域显示精简配置页；
4. 用户选择一种拍摄模式；
5. 人像、环境人像或群像模式可以按需指定关键人物；
6. 用户点击开始选图；
7. 系统处理当前文件夹同层级的全部符合条件资产；
8. 不确定的关键人物身份单独进入人工审核；
9. 系统只对未锁定资产应用最终允许写入的智能星级。

分析进度、完整复核、最终确认、写入时机、取消和失败恢复仍存在旧版设计，但本窗口没有把全部细节
重新冻结，见本文待研究部分。

## 4. 已确认的配置页 UI 要求

### 4.1 布局

- 中间区域采用弹性布局，不能依赖固定宽度。
- 所有拍摄模式名称和说明文字必须完整显示。
- 不允许出现文字逐字换行、相互覆盖、卡片溢出或主按钮被挤出页面。
- 宽窗口、半屏窗口和宿主左右栏同时展开时都必须保持可用。
- 内容过长时优先采用合理换行、列数调整和垂直滚动，不得缩小到无法阅读。

### 4.2 必须删除的内容

- 删除配置页中的任务摘要。
- 删除显示模型名称、运行时、推理设备等技术实现文本的区域。
- 删除关键人物页面的“已选择人物”独立区域。
- 删除重复、冗长、不能帮助用户完成当前操作的说明。

删除独立“已选择人物”区域不等于取消多关键人物，也不等于可以隐藏 A/B/C 身份标识。多人物身份
必须在更直接的位置表达，例如选中人脸框本身。

### 4.3 关键人物页面文案

提示应压缩为用户当前需要完成的动作，例如：

- 识别照片人物；
- 点击人脸框选择；
- 再次点击取消。

不应在主操作区反复解释模型、隐私、算法、优先级或完整业务背景。必要说明可以放在轻量帮助信息中，
但具体位置尚未冻结。

### 4.4 技术状态的表达边界

已确认不能向普通用户展示模型标识、执行器名称和技术参数。

是否保留“功能可用”“无法开始”等用户可理解的状态提示，以及该提示位于何处，本轮没有最终确认。
如果保留，只能表达用户下一步能否操作，不能退回技术术语展示。

### 4.5 当前已知预览问题

关键人物页面存在以下已知问题：

- 点击“识别照片人物”后可以出现人脸框；
- 底部照片预览曾出现黑屏或没有缩略图；
- 已选择人物计数曾持续显示为 0。

“已选择人物”独立区域已经决定删除，因此不再通过该区域修补计数展示。但多人物选择状态仍必须在
人脸框或其他直接反馈中可靠显示。

底部预览黑屏不能只通过样式掩盖。必须复现并确认它属于：

- 缩略图没有进入宿主请求队列；
- 当前渲染预览生成失败；
- Object URL 生命周期或缓存被过早释放；
- 图片路径、RAW 解码或 Tauri 调用失败；
- 切页和异步回调之间的状态竞争；
- 容器尺寸或图片尺寸计算异常。

当前暂存代码补充了可见页缩略图请求，这只是候选修复，尚未完成根因证明和桌面回归验收。

## 5. 已确认的拍摄模式逻辑

### 5.1 共同规则

- 模式选择的作用是切换真实的筛选证据、优先级、硬性条件和组内排序策略。
- 所有模式都可以复用基础画质证据，但不同模式不能得到完全相同的评分路径。
- 基础画质至少包括清晰度、曝光、明显运动模糊和构图可用性。
- 是否需要主体检测、人物状态、几何或专项算法由模式决定。
- 具体权重、阈值和星级分界仍须真实样片验证，尚未冻结。

### 5.2 自动模式

自动模式只执行两条主路径：

- 照片中有人：优先采用人像评分逻辑；
- 照片中没有人：按通用拍摄质量评分，重点检查光学素质、是否清晰和构图是否合理。

自动模式不应再通过横竖方向把无人照片猜成风光或产品。

为了可靠完成“有人/无人”判断，后续技术实现不能只依赖正面人脸；背影、远处人物、侧脸和被遮挡
人物需要人物或人体检测证据。

### 5.3 人像模式

人像模式的主要判断包括：

- 指定关键人物的身份条件；
- 关键人物或主体人物的眼睛状态；
- 表情技术状态；
- 脸部和眼部清晰度；
- 人脸及主体曝光；
- 整张照片的光学质量；
- 人像构图；
- 相似组或连拍去重与组内比较。

关键人物只是候选召回前提。照片包含关键人物后，还必须在人像证据上进行二次筛选，不能因为人物
出现就直接升星。

### 5.4 环境人像模式

环境人像沿用人像的主体表现判断，同时需要额外评估：

- 人物与环境的面积和位置关系；
- 环境是否提供有效语境；
- 背景是否干扰人物；
- 人物与环境的曝光、清晰度和层次是否平衡；
- 构图是否体现环境人像意图。

关键人物规则与人像模式一致。

### 5.5 群像模式

- 群像支持指定关键人物。
- 关键人物筛选逻辑与人像相同。
- 多位指定人物必须分别识别，不能把任意人脸状态当成指定人物状态。
- 还需要检查多人睁闭眼、遮挡、表情冲突、主体完整度和群体构图。

多位人物之间发生状态冲突时的合成方式尚未冻结，不能直接沿用旧的顺序加权逻辑。

### 5.6 风光模式

风光模式中以下证据为主要因素：

- 全画面和主体区域的清晰度；
- 光学质量；
- 曝光与高光、暗部细节；
- 构图和平衡；
- 地平线、前中后景层次和有效主体。

即使画面中有人，人物状态也只能作为辅助证据，不能反过来让风光照片使用人像主评分逻辑。

### 5.7 其他模式的方向

下列方向已经形成设计共识，但精确定义仍属于待验证项：

| 模式 | 应优先研究的核心证据                                       |
| ---- | ---------------------------------------------------------- |
| 街拍 | 动作、人物关系、姿态、画面时机、主体位置、技术可用性       |
| 动物 | 动物检测、眼部和主体清晰度、姿态、动作、遮挡、背景干扰     |
| 建筑 | 垂直线、水平线、透视、消失点、对称、畸变、细节             |
| 产品 | 主体完整度、边缘裁切、背景洁净度、反光、高光、色偏、细节   |
| 银河 | 星点清晰度、拖线、噪声与信噪比、光污染梯度、天空和前景层次 |

这些方向不是最终权重表。尤其街拍的“决定性瞬间”和产品、建筑、银河的专业标准，必须通过真实
摄影样片和摄影师判断继续定义。

## 6. 已确认的关键人物规则

### 6.1 显示范围

“指定关键人物”只在以下模式显示：

- 人像；
- 环境人像；
- 群像。

自动、风光、街拍、动物、建筑、产品和银河模式完全隐藏该入口。

这条决定覆盖旧文档中“自动和街拍也显示关键人物”以及“根据检测到的多人场景动态决定是否显示”
的规则。

### 6.2 多人物选择

- 允许一次选择多位关键人物。
- UI 使用人物 A、人物 B、人物 C 等稳定标识区分。
- A/B/C 首先表示身份区分，不自动等价为评分优先级。
- 是否还允许用户设置人物优先级，本轮未确认。
- 删除“已选择人物”侧栏后，A/B/C 应直接显示在选中的人脸框或照片反馈中。

### 6.3 候选召回和二次筛选

当用户选择一位或多位关键人物时：

1. 系统在任务照片中识别每位人物；
2. 只有确认包含全部已选人物的照片，才进入该模式的高价值候选集合；
3. 明确缺少任意一位已选人物的照片进入低星范围；
4. 候选集合再执行人像、环境人像或群像的二次筛选；
5. 二次筛选比较眼睛、表情、清晰度、曝光、构图和相似组差异；
6. 不能只因包含指定人物就直接获得高星。

“低星范围”具体是 1 星、2 星还是最高不超过某一星级，本轮没有冻结。

### 6.4 身份不确定

出现以下情况时，不得强行判定身份：

- 相似度接近；
- 一张照片中存在多个可能候选；
- 人脸太小、严重侧脸、遮挡或模糊；
- 多位指定人物发生匹配冲突；
- 检测结果只能说明“疑似”，不能确认。

这类照片进入独立“人工审核”分组：

- 显示“疑是关键人物”；
- 系统保持 0 星；
- 不继续套用自动星级逻辑；
- 由用户一眼确认并手动打星；
- 用户手动操作后按人工结果锁定。

### 6.5 身份数据边界

延续现有完全离线方向：

- 人脸样本和身份特征不得上传；
- 不建立跨任务持久人物库；
- 不推断年龄、性别、族群、健康、吸引力等敏感或无关属性；
- 最终持久数据不保存可用于身份识别的人脸特征向量。

特征的任务结束清理时机和异常恢复行为仍需在正式生命周期中再次验证。

## 7. 星级与人工审核语义

### 7.1 统一星级

- 所有拍摄模式使用同一套 1 至 5 星含义。
- 不为每个模式创造不同的星级语言。
- 模式差异来自评分证据和优先级，不来自改变“五星代表什么”。
- 0 星表示未由系统形成可采用评分，或需要人工审核。

本窗口没有重新冻结 1 至 5 星的完整文案和数值边界。旧文档中的“强烈推荐、推荐、需要确认、
偏弱、淘汰建议”可以作为讨论参考，但必须与本轮模式化评分和 0 星人工审核规则一起重新确认。

### 7.2 人工审核

目前明确需要进入人工审核的是“疑是关键人物”。

人工审核采用独立分组，不需要再增加复杂流程：

- 照片保持可见；
- 系统不自动打星；
- 用户直接手动判断；
- 用户操作后自动锁定。

除关键人物身份外，眼睛、表情、模式判断、拍摄组合和模型失败等低置信结果是否统一进入相同的
0 星人工审核区，本轮尚未确认。

### 7.3 相似组

- 模式评分应结合多张相似照片进行组内比较。
- 人像示例中的表情、睁闭眼、清晰度和构图需要在同组内比较。
- 不能让不同文件夹、不同场景和没有可比性的照片互相淘汰。

组内应该推荐多少张、星级如何与排名结合、独立照片如何评分、HDR/全景/堆栈如何保护，仍需与
现有双池复核需求一起重新研究。

## 8. 人工评分锁定：最高安全底线

### 8.1 已确认规则

智能选图的一切功能都建立在以下底线上：

> 禁止修改任何由用户手动操作过的星级。

具体规则：

- 用户手动设置星级后，默认锁定；
- 用户手动修改 AI 星级后，默认锁定；
- 用户手动清除星级到 0 后，仍然锁定；
- 锁定资产不得被后续智能选图修改；
- AI 自动产生且用户从未修改的星级默认不锁定，可被后续智能选图更新；
- 用户可以显式解锁；
- 解锁后，下一次智能选图允许重新修改该资产；
- RAW/JPEG 被视为同一拍摄资产时，任一成员的人工操作锁定整个资产；
- 关键人物人工审核中的手动打星同样产生锁定。

### 8.2 必须具备的 UI

- 用户必须能看见当前资产是否锁定；
- 锁定图标或状态必须有文字说明，不能只靠颜色；
- 用户必须理解“锁定后智能选图不会修改”；
- 用户必须能主动解锁；
- 批量解锁、单张解锁、RAW/JPEG 联动提示和解锁后的持续时间尚未冻结。

### 8.3 尚未冻结的锁定细节

- 解锁是永久保持，还是只允许下一次任务修改一次；
- AI 下一次写入后是否自动恢复未锁定状态；
- 是否允许在智能选图配置页批量查看或解锁；
- 复核页修改星级时是否需要额外提示；
- 手动颜色标签是否与星级采用同一锁；
- 历史 sidecar 没有来源字段时的迁移和显示方式；
- 外部程序在任务过程中修改评分时的冲突处理。

### 8.4 实现安全要求

为保证底线，正式实现至少需要两次保护检查：

1. 建立任务清单时排除受保护资产；
2. 真正写入前重新读取并检查锁定和来源状态。

任务启动后由用户或外部程序新增的人工操作必须阻止系统覆盖。任何读取失败、来源不明或并发冲突
都应保护现状并明确报告，而不是假定可写。

## 9. 当前项目的真实能力

### 9.1 可以继续复用的基础技术栈

当前项目使用：

- Tauri 与 Rust 承担本地任务和图片分析；
- ONNX Runtime 承担模型推理；
- macOS Core ML 与 Windows DirectML 执行器；
- image、imageproc 和现有渲染能力；
- feature-local 前端与 Rust 模块；
- YuNet 人脸检测；
- OCEC 睁闭眼分类；
- SFace 人脸身份向量。

结论：

- 基础技术栈能够承载不同模式的证据提取和评分架构；
- 不需要重写为 Python 客户端；
- 不需要引入云端服务；
- 不需要为十种模式分别运行十个大型模型；
- 新模型应优先转换为 ONNX 并复用现有运行时。

### 9.2 当前已有的分析证据

当前后端已经能够产生：

- 1600 像素分析缩略图；
- 全图拉普拉斯清晰度；
- 中心区域清晰度；
- 简单高光和暗部裁切曝光指标；
- 人脸检测；
- 左右眼睁闭眼候选；
- 人脸局部清晰度与曝光；
- SFace 身份向量；
- EXIF 时间、文件序列和 256 位感知哈希相似组。

人工来源识别已经具备良好基础：

- 没有可信 AI 来源记录的已有星级按人工处理；
- AI 结果被用户修改后转为人工；
- RAW/JPEG 任一成员存在人工结果时可以保护整个资产。

### 9.3 当前实现不能满足的部分

当前评分的主要问题：

- 十种模式基本只是在清晰度、中心清晰、曝光、人脸和睁眼之间换权重；
- 自动模式通过人脸数量和横竖方向猜模式；
- 表情状态固定为未知；
- 关键人物身份候选被明确禁止参与自动评分；
- 街拍瞬间、动物动作、建筑透视、产品背景和银河星点没有对应证据；
- 通用构图和审美没有可靠模型；
- 相似组只依赖时间、文件序列和感知哈希，对裁剪、姿态变化和语义相似支持有限；
- 当前目录扫描仍会递归子文件夹；
- 当前没有显式锁定和解锁状态；
- 当前星级阈值是统一固定值，没有通过每种模式的真实样片校准。

因此，当前实现只能作为基础证据原型，不能宣称已经支持十种模式的真实打星逻辑。

## 10. 推荐的目标技术架构

### 10.1 总体结构

不采用“十种模式各自重复运行一整套模型”，而采用：

1. 安全与范围门：当前层级、资产身份、人工锁定；
2. 共用证据提取层：画质、主体、人物、人脸、姿态、语义、相似度；
3. 模式策略层：决定哪些证据是主因素、辅助因素、硬门槛或不适用；
4. 组内排序层：在可比较照片中形成相对排名；
5. 不确定性层：把不能确认的结果送入人工审核；
6. 星级映射层：统一转换为 0 至 5 星；
7. 写入安全层：重新检查锁定后才允许更新。

### 10.2 推荐候选组合

面向实际离线发布、体积、授权和跨平台平衡，当前最推荐的候选组合为：

| 能力           | 候选                         | 计划用途                                         |
| -------------- | ---------------------------- | ------------------------------------------------ |
| 通用视觉特征   | DINOv2 ViT-S/14              | 题材特征、学习型相似组、构图特征、自有小型评分头 |
| 无参考画质     | ARNIQA 加确定性指标          | 通用技术质量、失真和模糊证据                     |
| 人物/动物/物体 | RT-DETRv4-S                  | 有人判断、主体类别、位置、完整度                 |
| 人体/动物姿态  | RTMPose 系列                 | 动作、遮挡、姿态和群体状态                       |
| 表情技术信号   | EmotiEffLib ONNX             | 表情过渡和稳定性辅助证据                         |
| 睁闭眼         | 保留 OCEC                    | 继续复用现有人眼状态能力                         |
| 人脸身份       | 先保留 YuNet 与 SFace        | 先做多尺度检测、多参考样本和阈值校准             |
| 连拍与相似组   | EXIF、感知哈希加 DINOv2 向量 | 提升裁剪、姿态变化和内容相似的分组能力           |
| 建筑与银河     | 专项确定性算法               | 避免通用模型误判专业摄影指标                     |
| 最终模式评分   | QRaw 自有小型组内排序模型    | 学习真实摄影师对同组照片的选择                   |

该组合只是优先验证顺序，不是已批准依赖清单。

### 10.3 专项算法

部分模式不能只依赖通用审美模型：

- 建筑：线段检测、消失点、垂直与水平偏差、透视和对称；
- 银河：星点检测、点扩散半高宽、星点椭圆率、拖线、天空噪声、信噪比和光污染梯度；
- 产品：主体完整度、边缘裁切、背景复杂度、高光、反光和色偏；
- 风光：多区域清晰度、地平线、动态范围、画面层次和显著性平衡；
- 人像：全图构图加原分辨率人脸和眼部局部精查。

当前只使用 1600 像素缩略图不足以可靠发现轻微虚焦。目标流水线应采用“全局缩略图分析 +
原分辨率主体局部复查”，并复用 QRaw 当前渲染结果。

### 10.4 最终效果最好的方向

没有现成公共模型能够直接理解 QRaw 对十种模式、组内相对选择和统一星级的完整定义。

最终效果最佳的方向是：

- 使用合法可分发的视觉模型提取证据；
- 建立按完整拍摄任务切分的真实验证集；
- 记录摄影师在每个相似组中的首选、备选和淘汰；
- 训练 QRaw 自有的模式化组内排序头；
- 公共审美分数只作为辅助证据，不直接决定最终星级。

## 11. 模型与依赖授权警戒

任何模型必须分别审查：

- 代码许可证；
- 模型权重许可证；
- 训练数据和衍生权重限制；
- 商业分发权；
- 模型转换和量化后的再分发条款；
- 第三方通知和署名要求。

当前已知注意事项：

- DINOv2 标准模型卡标注 Apache 2.0，可优先验证；
- ARNIQA 官方仓库标注 Apache 2.0，可作为画质候选；
- RT-DETRv4 仓库标注 Apache 2.0，并提供 ONNX Runtime 推理路径；
- MMPose 代码为 Apache 2.0，但具体姿态权重和数据集仍要逐项审查；
- EmotiEffLib 代码为 Apache 2.0，具体使用的模型权重仍需在引入时记录；
- InsightFace 代码可商业使用，但其官方训练数据和预训练模型包仅限非商业研究，不能直接随产品打包；
- Apple MobileCLIP 官方模型权重许可限定研究用途，不适合作为商业产品默认内置模型；
- IQA-PyTorch 当前采用非商业许可，不能因为其中包含 TOPIQ、MUSIQ 等模型就整体复制进产品。

如需训练和导出，可以在研发环境使用 Python、PyTorch、ONNX 导出、量化和性能分析工具；这些工具
不应成为 QRaw 用户端运行依赖。

## 12. 当前还没有研究或确认完成的产品问题

- 硬性淘汰或降星条件；
- 不确定时的处理；

尤其需要继续讨论：

- 为每个证据输出置信度和不可用原因。

### 13.6 相似组

- 使用真实连拍、轻微重构图、裁剪、人物动作变化和随机邻近照片建立测试集；
- 比较当前时间加感知哈希与加入 DINOv2 向量后的效果；
- 防止分组链式漂移；
- 防止 HDR、全景、堆栈和动作序列被误当普通重复照片；
- 确定组内排名、推荐数量和独立照片策略。

### 13.7 模型 ONNX 与跨平台执行

每个候选模型都必须完成：

- 固定输入输出契约；
- ONNX 导出和数值一致性；
- Core ML 执行器完整图运行；
- DirectML 执行器完整图运行；
- 不支持算子和动态形状检查；
- 冷启动、批处理、峰值内存和显存测试；
- 量化前后准确率测试；
- 模型缺失、损坏和版本不匹配测试；
- macOS 与 Windows 安装包实际加载测试。

项目当前禁止静默 CPU 降级，因此不能只证明模型“可以由 ONNX Runtime 加载”，必须证明完整计算图
在目标执行器上能够稳定完成。

### 13.8 黑屏预览专项

- 在真实 Tauri 桌面环境复现，不只在浏览器开发服务器验证；
- 覆盖 JPEG、RAW、有调整和无调整照片；
- 检查缩略图请求是否实际触发并回填 store；
- 检查 GeneratePreviewForPath 的错误和返回字节；
- 检查 Object URL 创建、引用计数、切图和回收；
- 为加载失败增加用户可见状态和重试；
- 快速翻页和反复打开关闭关键人物面板时做压力测试；
- 验证缩略图不黑屏、主预览不黑屏、内存不会持续增长。

### 13.9 数据集与效果验证

在冻结权重和星级前，必须建立按完整拍摄任务划分的验证集，至少覆盖：

- 十种拍摄模式；
- 连拍、相似组和独立照片；
- 不同机型、镜头、焦段、光照和 ISO；
- RAW 与非 RAW；
- 横图、竖图、裁剪和当前调色状态；
- 小脸、侧脸、遮挡、眼镜、多人和相似人物；
- 建筑创意透视；
- 产品不同背景和反光材质；
- 银河、星空、堆栈和星轨；
- 摄影师明确的首选、备选、可用和淘汰判断。

验证集必须与阈值调试数据分离。最终至少测量：

- 人物存在判断召回和误报；
- 关键人物全部出现的召回率；
- 关键人物误匹配率；
- 疑似身份进入人工审核的覆盖率；
- 同组首选进入 Top-K 的比例；
- 各模式星级与摄影师排序的一致性；
- 人工锁定被错误修改的数量；
- 任务耗时、峰值内存、失败率和取消响应。

阈值必须先书面确定，再在未参与调参的样片上验证。

### 13.10 性能和发布资源

- 确定首发 macOS 和 Windows 设备矩阵；
- 重新验证旧文档中的 1000 张约 5 分钟目标是否仍适用于新增模型；
- 记录渲染、人脸、身份、画质、检测、姿态、分组和排序各阶段耗时；
- 确定模型安装包增量、磁盘、内存、显存和冷启动预算；
- 只按需要的模式运行专项模型；
- 复用证据并避免每种模式重复推理；
- 验证任务取消和模型错误不会影响 QRaw 其他功能。

### 13.11 上游同步回归

每次同步 CyberTimon/RapidRAW 后必须检查：

- 智能选图实现是否仍集中在 feature 目录；
- 上游左右栏没有被二开样式影响；
- 统一挂载点和 Tauri command 注册仍然最小；
- 宿主图片列表、缩略图请求和渲染接口契约是否变化；
- sidecar 星级与来源写入路径是否变化；
- 中部配置页在新上游布局下仍然弹性适配；
- 不通过复制上游逻辑到 feature 内规避接口变化。

## 14. 开发前验收 Gate

### G0：需求一致

- 本文与正式需求、UI、架构和实施清单不存在相互冲突的规则；
- 每个模式都有书面证据、优先级、不确定性和星级策略；
- 锁定、解锁、0 星人工审核和 A/B/C 身份语义已经冻结。

### G1：数据安全

- 所有手动设置、修改和清零都能产生锁定；
- RAW/JPEG 资产保护一致；
- AI 结果只有在未锁定时可更新；
- 写入前重新检查；
- 自动化测试中人工结果被覆盖次数为 0。

### G2：配置页与关键人物流程

- 只修改中部 feature UI；
- 文字完整，布局弹性；
- 任务摘要和技术文本已删除；
- 关键人物只在三个模式出现；
- A/B/C 选择、取消和反馈清楚；
- 底部缩略图和主预览不黑屏；
- 键盘和无障碍操作可用。

### G3：效果

- 十种模式不再只是四项基础信号换权重；
- 自动模式有人/无人路由可靠；
- 关键人物全部出现、缺失和疑似状态可靠；
- 相似组 Top-K 与摄影师判断达到预先冻结的门槛；
- 建筑、产品、动物和银河具有对应专项证据；
- 未达到门槛的能力不以确定性文案发布。

### G4：跨平台与发布

- 所有批准模型完成许可证和分发审查；
- Core ML 与 DirectML 实机完整图通过；
- 安装包、内存、显存和性能预算通过；
- 模型异常只影响智能选图，不影响 QRaw 主功能；
- 同步上游后的隔离和回归检查通过。

| -------------- | -------------------------------------------------- | ------------------------------------------- |

## 16. 建议的下一步顺序

1. 先把本文中的产品未决问题逐项确认，尤其是星级、A/B/C、解锁语义和完整复核流程；
2. 同步修改正式需求、UI 生命周期、技术架构和实施清单，消除递归、关键人物和任务摘要冲突；
3. 完成配置页现有暂存修改的真实桌面验证，优先解决黑屏、模式隐藏和 A/B/C 反馈；
4. 实现并测试平级目录范围和显式锁定安全闭环；
5. 建立真实样片验证集和摄影师标注规则；
6. 按 DINOv2、ARNIQA、RT-DETRv4、RTMPose、EmotiEffLib 的顺序做独立技术刺探；
7. 先完成可解释的模式规则版本，再用真实数据训练 QRaw 自有组内排序模型；
8. 每个阶段通过对应 Gate 后再进入生产实现，不用占位权重或文案宣称能力完成。

## 18. 一句话基线

智能选图必须在不侵入上游、只处理当前文件夹同层级、绝不覆盖人工锁定星级的前提下，使用共用证据
提取和真正不同的模式策略完成组内打星；关键人物只属于人像、环境人像和群像，全部指定人物确认出现
后才进行二次筛选，疑似身份保持 0 星进入人工审核；所有尚未经过真实样片、许可证、Core ML、
DirectML 和性能验证的模型能力都不得宣称已经完成。
